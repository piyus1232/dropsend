# Upload Receipt

Users upload photos or screenshots of receipts. Images are stored in a private Supabase Storage bucket, a `receipts` row tracks each one, and an Inngest worker verifies each upload in the background. Status changes reach the UI live through Supabase Realtime. No OCR yet; the worker is where it will hook in.

Built in four layers:

1. Database schema, Storage bucket and policies.
2. Upload API routes (signed upload URLs) and the Realtime client hook.
3. shadcn sidebar and the Upload Receipt page.
4. Inngest worker for background processing.

## Decisions

- **Limits:** JPG, JPEG, PNG and WebP only; max **1 MB** per file; max **4 files** per upload.
- **Upload path:** Browser uploads **directly to Storage with signed upload URLs** (not through an API route). Avoids Vercel's ~4.5 MB request body limit, uploads files in parallel, and gives per-file status. The server still validates requests, creates the rows and decides the storage path.
- **One pipeline:** A single upload is a batch of one. Every upload goes through the same steps and statuses.
- **Status changes are server-only:** Users have no `update` policy on `receipts`, so they can't set a status or hash themselves through the public API. All status changes happen server-side with the Supabase secret key (see [Secret key](#secret-key)).
- **Background processing:** One Inngest event (`receipt/uploaded`) per receipt; each receipt is its own function run.
- **Live updates:** Supabase Realtime (`postgres_changes` on `receipts`), not Inngest Realtime.
- **Duplicate files:** The image's SHA-256 hash is stored, but duplicates are **not** detected yet. That belongs to the duplicate-detection feature.
- **Abandoned uploads:** Rows stuck in `uploading` for over 10 minutes are marked `failed` lazily when the user lists their receipts. No timer job.
- **Failed receipts** can be retried or deleted from the UI.

## Database

Migration: `supabase/migrations/20261007120000_create_receipts.sql`. Apply it with the Supabase CLI (`supabase db push`).

### `receipt_status` enum

| Status | Meaning |
| --- | --- |
| `uploading` | Row created, signed upload URL issued, file not verified yet. |
| `uploaded` | File verified by the worker. |
| `processing` | OCR running (future). |
| `needs_review` | OCR done, waiting for user review (future). |
| `saved` | User saved the expense (future). |
| `failed` | Upload or processing failed; reason in `error`. |

The future statuses are already in the enum, so OCR won't need a migration to add them.

### `receipts` table

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | Generated by the server before insert (needed for the storage path). |
| `user_id` | `uuid` | → `auth.users`, `on delete cascade`. |
| `batch_id` | `uuid` | Shared by all receipts uploaded together. |
| `storage_path` | `text` unique | `{user_id}/{receipt_id}.{ext}`. |
| `original_filename` | `text` | |
| `mime_type` | `text` | Check: `image/jpeg`, `image/png`, `image/webp`. |
| `size_bytes` | `integer` | Check: `> 0` and `<= 1048576`. |
| `image_hash` | `text` | SHA-256 hex, set by the worker. For duplicate detection later. |
| `status` | `receipt_status` | Default `uploading`. |
| `error` | `text` | User-facing failure reason. |
| `created_at`, `updated_at` | `timestamptz` | `updated_at` maintained by a trigger. |

Indexes: `(user_id, created_at desc)` for the recent-uploads list; `batch_id`.

### Row Level Security

Users can:

- **select** their own rows.
- **insert** rows only for themselves, only with status `uploading`, and only with a `storage_path` inside their own folder.
- **delete** their own rows.

There is no **update** policy. Status, hash and error are changed only server-side with the secret key.

Realtime is enabled on `receipts` (added to the `supabase_realtime` publication). Realtime respects RLS, so a client only receives changes to its own rows.

### Storage

- **Bucket `receipts`:** private, 1 MB file size limit, allowed types `image/jpeg`, `image/png`, `image/webp`. This is a second server-side check on top of the API's own.
- **Path:** `{user_id}/{receipt_id}.{ext}`.
- **Policies on `storage.objects`:**
    - **select / delete:** only inside the user's own `{user_id}/` folder.
    - **insert:** only inside the user's own folder **and** only to a path that already has a matching `receipts` row. Files can't be uploaded outside the upload flow.

## Upload Flow

```
1. Browser ──(file name, size, type)──► POST /api/receipts/upload-urls
                                         validates, inserts rows (uploading),
                                         returns a signed upload token per file
2. Browser ──(file bytes)──► Supabase Storage    (uploadToSignedUrl, in parallel)
3. Browser ──(uploaded ids, failed ids)──► POST /api/receipts/complete
                                         records failures, sends one
                                         `receipt/uploaded` event per receipt
4. Inngest worker (per receipt): checks the image exists → checks the real file
   type → computes SHA-256 → status `uploaded` (or `failed`)
5. Realtime pushes each status change to the browser.
```

## API Routes

All routes require a session (401 otherwise). Bodies are JSON; errors are `{ "error": string }`.

| Method | Route | Body | Response |
| --- | --- | --- | --- |
| `GET` | `/api/receipts` | — | `{ receipts: (Receipt & { preview_url })[] }`: 50 most recent, with signed preview URLs valid for 1 hour. First marks stale `uploading` rows as `failed`. |
| `POST` | `/api/receipts/upload-urls` | `{ files: { name, size, type }[] }` (1–4) | `201 { batchId, uploads: { receiptId, path, token }[] }`. `token` is `null` if the URL couldn't be created (that receipt is marked `failed`). |
| `POST` | `/api/receipts/complete` | `{ uploaded: uuid[], failed: { id, error }[] }` | `{ success: true }`. Ignores ids that aren't the user's or aren't `uploading`. |
| `POST` | `/api/receipts/[id]/retry` | `{ canReupload: boolean }` | See [Retry](#retry). Only for `failed` receipts (409 otherwise). |
| `DELETE` | `/api/receipts/[id]` | — | `{ success: true }`. Removes the image, then the row. |
| `GET/POST/PUT` | `/api/inngest` | — | Inngest serve endpoint. Public in the proxy; Inngest itself calls it and verifies requests with the signing key. |

### Retry

1. **The image is in Storage:** reset to `uploading` and send the event again → `{ action: "queued" }`.
2. **The image is missing and `canReupload` is true** (the browser still has the original `File` from this session): reset to `uploading` and return a new signed upload token → `{ action: "upload", path, token }`. The browser uploads, then calls `/complete`.
3. **The image is missing and the browser no longer has the file:** `409` telling the user to delete the receipt and upload it again.

Resetting to `uploading` also bumps `updated_at`, which restarts the 10-minute stale timer.

### Validation (`src/lib/receipts/schemas.ts`)

The zod schemas are shared by the browser (to reject bad files on selection) and the routes. File type must be one of the allowed MIME types, size `1..1048576` bytes, and a batch has 1–4 files. The constants live in `src/lib/receipts/constants.ts` and must stay in sync with the migration.

## Background Processing (Inngest)

- **Client:** `src/inngest/client.ts` (`id: "dropsend"`).
- **Event:** `src/inngest/events.ts`: `receipt/uploaded` with `{ receiptId, userId }`, typed with `eventType()` and a zod schema.
- **Function:** `src/inngest/functions/process-receipt.ts` (`process-receipt`).
    - One step, `verify-image`, which calls `processReceipt()` in `src/lib/receipts/process.ts`.
    - `retries: 3`.
    - `concurrency: { key: "event.data.userId", limit: 2 }`, so one user's batch can't hog the queue.
    - `onFailure`: once retries run out, marks the receipt `failed` ("Processing failed. Please try again.").
- **Errors in `processReceipt()`:**
    - **File problems fail immediately, with no retry:** the image is missing ("The image was not uploaded."), or its leading bytes don't match the declared type ("not a valid JPG, PNG or WebP image"; the file is also deleted).
    - **Unexpected errors** (database, Storage) are thrown, so Inngest retries them.
    - **Safe to run twice:** it only acts on receipts still in `uploading`. A deleted receipt, or one already handled, is a no-op.
- **Sending events:** `enqueueReceiptProcessing()` sends all events in one `inngest.send` call. If Inngest can't be reached, the receipts are marked `failed` ("Couldn't start processing.") and the user can retry.
- **Local dev:** `INNGEST_DEV=1`, then run `bun run dev:inngest` (from the root or `apps/web`) next to `bun dev`. The dashboard is at http://localhost:8288.
    - `inngest-cli` is a dev dependency listed in `trustedDependencies`, because Bun skips the install script that downloads its binary otherwise. `bunx` and `npx` don't work for it under Bun.

## Secret Key

`src/lib/supabase/admin.ts` → `createAdminClient()`. It uses `SUPABASE_SECRET_KEY` and **bypasses RLS**.

- It imports `server-only`, so the build fails if browser code imports it.
- It's used only for status changes (`process.ts`, retry reset) and the worker, which has no user session.
- Anything that uses it must check ownership first. Routes do this by reading the receipt through the user's own (RLS) client before using the admin client.

`src/lib/auth/get-user.ts` → `getSessionUser()` returns the RLS-bound server client and the current `userId` (from `getClaims()`).

## Realtime

`src/hooks/use-receipts.ts` → `useReceipts()`:

- Loads `/api/receipts` once, then subscribes to `postgres_changes` on `public.receipts`.
- **UPDATE:** merges the new row into the list.
- **DELETE:** removes the row.
- **INSERT, or a row becoming `uploaded`:** reloads the list, because new signed preview URLs can only be created server-side.

## Frontend

### Sidebar (`src/components/app-sidebar.tsx`)

- shadcn `Sidebar` in the `(protected)` layout replaces the old header.
- **Nav:** Dashboard (`/dashboard`), Upload Receipt (`/upload`). The current page is highlighted.
- **Footer:** user's name and email, Log out button.
- Collapsible with the toggle button or Ctrl/Cmd+B; the state is remembered in the `sidebar_state` cookie. On mobile it opens as a sheet and closes on navigation.
- The root layout wraps the app in `TooltipProvider`, which the sidebar needs for tooltips when collapsed.

### Upload page (`/upload`)

`src/app/(protected)/upload/page.tsx` renders `ReceiptUpload` (`src/components/receipts/`):

- **`receipt-upload.tsx`:** connects the drop zone and the list. Keeps the original `File` for each uploaded receipt in memory (lost on reload), so Retry can re-upload.
- **`receipt-dropzone.tsx`:**
    - Drag and drop, or click to open the file picker.
    - Selected files show thumbnails. Invalid files show their error and are skipped. Selections beyond 4 files are dropped with a toast.
    - "Upload N receipts" button, with toasts for success and errors.
- **`recent-uploads.tsx`:**
    - Loading skeletons, then an empty state or one row per receipt.
    - Each row: thumbnail (click to open full size), file name, status badge (with a spinner while uploading), size and time, or the error for failed receipts.
    - Retry (failed only) and Delete (with an `AlertDialog` confirmation).

Browser helpers are in `src/lib/receipts/client.ts`: `uploadReceipts`, `retryReceipt`, `deleteReceipt`, `fetchReceipts`, `validateReceiptFile`. Formatting helpers (`formatBytes`, `formatRelativeTime`) are in `src/lib/format.ts`.
